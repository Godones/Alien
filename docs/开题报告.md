# 开题报告

## 选题依据

### 选题背景和意义

现代主流操作系统通常由内核和用户空间程序两部分构成，其中内核由多个复杂的子系统组成，例如文件子系统、网络子系统以及大量的驱动模块。各子系统及驱动模块运行在共享的内核地址空间中，模块之间复杂的依赖关系导致单个模块的错误可能引发其它模块乃至整个系统的崩溃。根据内核补丁的统计显示【】，许多漏洞是由于不正确的内存操作导致的，比如缓冲区溢出，释放后使用、双层释放【】等。随着内核代码规模的不断扩大(截至2021 年，Linux 内核 5.11 版本拥有约 3034 万行代码。大约 14% 的代码属于核心，包括架构特定代码、内核代码和内存管理代码，而 60% 是驱动程序【】) 以及不安全编程语言的广泛应用，这些问题变得愈加严重。为增强内核的安全性，近年来引入了多种技术和工具(ASLR【】，Stack Canaries 【】,DEP【】)，这些方法虽然一定程度上降低了内核漏洞被利用的可能性，但没有从根本上解决错误传播的影响，内核子系统需要隔离来限制单个模块中漏洞的影响。

过去，受限于性能有限的设备，在面对安全性和高性能的选择时，开发人员不得不选择后者。如今，CPU的架构取得了许多进步，CPU的性能已经不再是限制内核开发的主要因素。然而，在内核子系统之间引入隔离以提高整个系统的可靠性和安全性依然困难。一些研究作品【FlexOS，CuriOS】尝试利用先进的硬件手段来为内核提供隔离【MPK】【EPT】，由于现代CPU提供的用于高效、细粒度隔离的接口通常只针对用户态，这些作品往往只针对unikernel形态的操作系统，无法简单地迁移到宏内核架构中，即使一些硬件接口可以用于宏内核的隔离，但通常需要对内核进行侵入式的修改，这在无形之中又带来了更多的安全问题。因为这些硬件接口并非是为了内核隔离而设计，即使经过良好的优化依然具有不可接受的开销，与特定硬件的绑定还使得这些方法缺乏灵活性。

也有研究抛开硬件隔离的思路，尝试在软件层面提高系统的可靠性和安全性。【Spin，Verve，Biscuit】操作系统分别使用Jave、C#、Go语言进行实现，这些内存安全语言都包含一个运行时用于垃圾回收机制。即使使用最先进的垃圾回收算法，在面对速度越来越快的高性能设备时，其开销依然不可忽视。与使用特殊硬件接口进行隔离的方案类似，这种方案显然还不可能应用在商用操作系统当中。确保内存安全的另一条截然不同的道路是形式化验证，Sel4【】是第一个经过形式化验证的微内核，通过将所有内核子系统转移到用户空间，整个内核只保留了一个最小的经过验证的可信计算基础(TCB)。CertikOS则是第一个完成具有细粒度锁定的完整通用并发操作系统内核功能正确性证明的宏内核。正如这些作品所展示的那样，在C语言这样的低级系统语言上进行形式化验证需要大量的手工工作，并且随着系统功能的增加而变得更加困难。

随着编程语言的演进，诸如Rust【】等兼具高性能和内存安全的现代语言为实现高效、轻量化且细粒度的隔离提供了新思路。Rust 是一门以内存安全、并发支持和高性能为核心设计的编程语言，为实现安全的系统级编程提供了独特的语言机制。通过静态分析和编译时验证，Rust 在无需运行时垃圾回收的情况下提供了强大的内存安全保障，与传统依赖垃圾回收的语言（如 Java 或 C#）相比，Rust 在性能和资源控制上更具优势。在 Rust 中，所有权模型是其安全机制的基础，它通过精确管理资源生命周期，消除了常见的内存错误，例如释放后使用和数据竞争。借用检查器进一步扩展了这一能力，它在编译时对程序中的所有引用进行跟踪和验证，确保引用总是安全且有效，从根本上避免了悬垂指针等问题。这种语言级别的安全保障与操作系统模块隔离的需求高度契合，因为模块隔离依赖于严格的内存和资源边界控制，以防止模块间的干扰和恶意行为。近年来Rust在操作系统开发方面引起了广泛关注，Linux社区也已开始接纳由Rust实现的驱动程序【】。

为了探索Rust语言对操作系统设计的影响，以及其在内核中实现高效、细粒度隔离的能力和优势，本课题设计了一种称为隔离内核的操作系统架构。隔离内核由一个负责启动和安全抽象的TCB和完全使用safe Rust实现的域集合组成，TCB封装了所有unsafe操作并向域提供基本服务，域是内核子系统和模块的抽象，依靠Rust语言的类型系统和内存安全实现隔离而不是硬件接口，域的故障被隔离并被安全地展开以正确释放资源。在隔离的基础上，我们进一步展示了实现域的热升级的可能性。

### 国内外研究现状

编程语言的发展也在促进操作系统的设计。数十年来，为了解决不同的问题，许多高级语言被发明出来，虽然普通用户可以使用高级现代语言来方便地编写应用，但在性能敏感的场景中，C和汇编依然是首要选择。对于操作系统内核这种性能极度敏感的基础设施，C和汇编依然占据主要地位。如今，内存安全和高性能的编程语言开始展现他们在改进和提高底层系统的能力。

【Verve】提出并实现了操作系统 Verve，这是一种使用类型化汇编语言（TAL）和自动化定理证明技术验证类型安全和内存安全的操作系统。Verve采用分层结构设计，其中低层的Nucleus负责与硬件和内存的交互，并通过Hoare逻辑进行正确性验证，而高层的内核和应用则使用安全的C#代码编写，并编译为TAL后自动验证其安全性。通过这种设计，Verve实现了对系统各个组件的静态验证，包括运行时系统、设备驱动和应用程序的安全性，从而在操作系统中消除了缓冲区溢出和内存悬挂等常见低级错误。【Biscuit】探讨了使用高级语言Go编写Posix内核的可行性，其开发充分利用了Go语言的类型安全、垃圾回收和并发机制。这些工作有效地证明了现代高级语言可以从底层设计上降低操作系统内核发生的错误并在高层简化对操作系统的验证工作，然而，基于垃圾回收的内存安全语言还是限制了他们的功能性和扩展性。与这些语言不同，Rust不使用垃圾回收而是基于线性类型的所有权模型实施类型和内存安全, 这可以进一步解决这些语言面临的主要问题。

Rust在操作系统方面的早期成果包括一系列微内核、嵌入式系统、unikernel，比如【Redox】【TockOS】【RustyHermit】【Drone】【Bern】等。Redox利用 Rust 开发了基于微内核的操作系统，其中微内核和用户级设备驱动程序都用 Rust 实现，但可自由使用不安全的Rust。与传统的微内核类似，设备驱动程序位于用户空间，使用IPC进行通信，使用硬件MMU实施用户程序的隔离。其它的一些内核也与传统上使用C开发的内核相似。简而言之，这些系统都利用 Rust 作为 C 语言的安全替代品，但并没有探索 Rust 在类型和内存安全之外的功能。Tock是一个针对有限硬件支持的嵌入式操作系统，其核心结构是一个核心内核和一系列设备驱动程序(capsules)，为了进行驱动程序的隔离，Tock禁止在capsules使用不安全的rust，但在capsules之间，Tock不限制他们通信的方式。Tock提出的许多原则使得我们对Rust提供的安全保证有了更进一步的认识，不过，我们认为这些还不足以支撑在通用操作系统中实现高效、细粒度的隔离。和Tock一样意识到Rust语言在实现隔离系统的潜力的还有【Netbricks 】和【Splinter】，NetBricks结合 Rust语言安全和零拷贝软件隔离技术，提供高效的内存和网络数据包隔离，而Splinter 允许租户动态加载安全扩展代码，从而在多租户内存键值存储系统上减少存储与计算之间的数据移动。与我们的目标相距甚远，这些系统都不支持动态加载卸载子系统，实现子系统的故障隔离和恢复，也不支持子系统的热升级。

**Redleaf**  是一个使用Rust开发的微内核，旨在探索语言安全性对操作系统组织结构的影响，尤其是在实现细粒度隔离方面的潜力。不同于依赖硬件地址空间的传统操作系统，RedLeaf 利用 Rust 的类型和内存安全特性实现隔离。这种设计避免了昂贵的硬件隔离机制，使得轻量级隔离成为可能，并且降低了性能开销。RedLeaf 的核心抽象是语言支持的隔离域（Domain），这些域作为独立的隔离单元，可动态加载和安全卸载，并且崩溃时不会影响其他域的执行。与之前利用语言机制实现子系统隔离类似【J-Kernel】【KaffeOS】【Singularity】，RedLeaf中隔离的实现依赖以下原则：堆隔离、可交换类型、所有权追踪、接口验证和跨域调用代理。堆隔离确保每个域的私有堆不会被其他域访问，从而支持域的独立终止。共享堆则允许跨域数据的零拷贝通信，而可交换类型的约束保证了安全性。所有权追踪机制记录了共享对象的拥有者，从而在域崩溃时可以安全地回收资源。跨域调用由代理对象管理，这些代理不仅确保了安全性，还支持线程回滚，从而在域崩溃后返回错误而非引发更严重的故障。尽管redleaf在使用Rust实现高效、细粒度的隔离子系统上已经迈出了一大步，然而这还没有完全发挥出Rust语言的所有能力。首先，Redleaf缺乏对safe和unsafe边界的划分，虽然其要求开发的域中不能包含unsafe代码, 但是大多数域都依赖于域相关的可信库，而可信库中大量的unsafe代码破坏了Rust语言提供的安全保证，使得整个系统中完全由safe代码构成的部分比例大大减少。其次，Redleaf依靠状态检查点机制来实施故障隔离，然而，仅仅靠检查点状态的保存和恢复是无法正确释放由故障导致的资源泄露的，如果没有将检查点到故障点之间的分配的资源释放掉，即使可以再次对已经发生故障的域发起请求，域仍然处于一个不正确的状态。最后，Redleaf没有意识到，对子系统的隔离可以带来更多有趣的扩展功能，比如实现子系统的热升级。

**Theseus** 是另一个从零开始使用 Rust 编写的实验性操作系统，它重新思考了操作系统的结构和状态管理问题。其聚焦于解决现代操作系统中普遍存在的状态泄漏（state spill）问题，这种问题导致模块间的强耦合，严重阻碍了系统的演进、容错性和灵活性。Theseus 的设计核心在于通过明确划分操作系统模块边界、最大化利用语言特性以及消除模块间状态泄漏，构建一个可以动态演进和高效容错的系统。Theseus 中的每个模块被称为“cell”，它们是运行时独立且可动态加载或替换的单元。这种设计确保了系统在运行时的灵活性，支持模块的实时热插拔和无中断更新。Theseus 通过 Rust 的内存安全和类型安全特性，将许多传统由操作系统负责的任务（如内存管理和资源回收）转移到编译器层面。这种“内在化设计”（Intralingual Design）减少了操作系统本身需要维护的状态量，简化了状态管理。特别是，Theseus 实现了无状态的模块交互，使得模块更新或恢复时无需担心状态一致性问题。此外，通过模块化的设计理念，Theseus 使得故障模块可以被独立隔离并恢复，从而提升了系统的容错性。不幸的是，由于一贯的特权级分离设计，现代商用操作系统内核子系统中保存了大量用户任务的状态，各个子系统之间依靠复杂的状态数据进行交互，为了实现Theseus提倡的无状态设计方法，商用操作系统内核需要进行彻彻底底的推翻和重构，这在当前显然还不能实现。虽然现代操作系统并不缺乏进行热升级的方法，但这些方法往往局限于函数级别livepatch[]、kpatch[]、Ksplice[]),或者局限于某一个特定的内核模块【】，其最大的困难就在于缺乏一种通用的方法来存储和恢复子系统的状态数据。我们认为，结合Rust提供的高效、细粒度隔离能力，我们可以在保持传统模块实现的方式上，为隔离的模块增加新的存储和恢复状态数据的机制，从而实现隔离模块的热更新。

**Rust For Linux**  在 Linux 内核中引入 Rust 被视为一种在不牺牲性能的前提下增强内核安全性的方式。虽然 C 语言仍然是内核开发的主要语言，但 Rust 提供了一种潜在的途径，使开发人员能够编写更加健壮和安全的代码。特别是对于那些与用户交互较多的模块，使用 Rust 可以显著减少由内存错误引发的攻击面。Rust 还支持现代编程特性，如模式匹配、泛型和 trait，这些特性有助于编写简洁、易于维护的代码。对于 Linux 内核的开发者来说，这意味着可以用更少的代码实现相同的功能，同时保持代码的可读性和可维护性。此外，Rust 的生态系统也在快速发展，Cargo 包管理器和丰富的第三方库使得开发过程更加高效。 我们认为，Rust语言不应该仅仅作为改善C代码质量的一个可选择项，基于Rust语言而设计的隔离机制也不应该局限于原型系统中。相反，我们应该将这些设计方法有机地与Linux内核进行融合，在不破坏已有代码的前提下，进一步提高内核的安全性和可靠性。

## 研究内容

详细地来说，我们在隔离内核中引入了以下5个设计原则，以支持内核子系统之间的隔离和实时更新,而不会违反语言提供的安全保证和丢失程序运行的状态。

1. 内核分解与抽象：为了实施隔离，我们首先需要分解内核。我们将内核划分为允许使用unsafe代码的TCB和只能使用safe的域集合，TCB被进一步分为运行时和domain lib两个部分。利用Rust的包管理机制，我们将每一个功能独立的内核子系统划分为一个个独立的包(域)，同时，我们为这些域定义了一组良好的接口(rust中的trait)，每个域都需要实现特定的一个或者多个接口，域对外表征就是一个trait对象。
2. 内存隔离: 为了确保域内部的内存安全和域之间的内存隔离，我们依靠两个关键部分。首先，domain lib作为TCB的核心，为域的实现提供了对所有unsafe操作和底层资源的封装和高级抽象，所有的域完全依赖domain lib和 Rust核心库并且禁止使用unsafe接口。其次，我们为每个域管理一个私有堆和共享堆，私有堆用于域的正常堆分配，并且不能指向其它域的私有堆内存, 共享堆则用于域间调用所需的数据交换。利用Rust的类型系统，我们静态地保证共享堆上的数据不能指向域的私有堆数据，从而避免通过共享堆泄露域内部的数据。
3. 故障隔离与恢复: 内存隔离促进了故障隔离的实施，有了内存隔离，域内部的资源得到了保护。但是我们还需要保证域内的故障不会影响其它的域，因此我们为每个域生成故障捕获点，域内发生的故障最终终止于捕获点而不会蔓延到其它域中，为了正确释放捕获点与故障点之间分配的资源，我们为内核资源结构实现了Drop trait。正确的资源释放确保了故障恢复的有效性，我们允许在域发生故障后重启对域的调用。
4. 状态保存和恢复: 为了使得域可以进行热升级，域需要确定是属于无状态域还是有状态域，对于无状态域来说，不需要保存域中的任何数据，因为其提供的服务不依赖内部的状态。对于有状态域，我们为域分配一个自定义堆，域将需要在升级后继续使用的状态数据保存在这个堆上，我们提供与普通堆分配类似的分配接口以及索引接口，以简化状态数据的存储和索引操作。
5. 域代理：我们通过代理来完成域的热升级和故障隔离和恢复，这对开发者来说是透明的。故障隔离代理生成故障的终止点，代理可以有选择地进行故障重启，重新发出相同的调用。热升级代理执行共享堆数据的所有权转移，为热升级记录必要的信息，在热升级期间负责维护域状态数据的同步。为了降低域热升级对用户任务的影响，无状态域采用RCU机制进行快速升级，有状态域使用锁确保状态的一致性，但配合热升级代理收集的信息和运行时代码修改技术，我们只需要在热升级期间使用锁。



## 研究方案

在5个原则的指导下，本课题使用Rust开发一个包括多个域的隔离内核原型Alien。在这个系统中，所有的内核功能被合理地划分为独立的内核模块，进而实施我们的隔离原则。这些域实现Linux系统的大量功能：任务管理，多核调度，中断分发，文件系统，网络套接字以及许多设备驱动。与LKM类似，这些域是被动态地加载到内核中的，启动初期，内核仅仅加载了几个必须的域，在系统运行过程中，其它的域因为用户需求而被逐步加载到内核中。在隔离的基础上，我们为系统中的大量域实现热升级，从不需要状态保存的简单驱动程序到包含复杂数据的文件系统。为了评估隔离内核架构的通用性，我们在Linux中开发域基础设施，并将null和nvme驱动改造为域，这两个使用广泛的驱动程序可以说明基于语言机制实现内核隔离的有效性和通用性。

## 预期研究成果

本课题做出了以下贡献:

- 我们提出了隔离内核架构, 以探索基于语言机制实现高效、细粒度的内核子系统隔离。在确保隔离的基础上，我们还赋予了对内核子系统进行热升级的能力。
- 基于隔离内核架构，我们设计并实现了一个隔离内核原型Alien，我们还在Linux系统中应用了隔离内核架构，并实现了常用内核驱动程序的隔离改造
- 我们对Alien和Linux 驱动进行了全面评估，结果表明，在不牺牲性能的情况下，基于语言机制的方法可以为内核带来高效、细粒度的隔离，提高内核的安全性和可靠性，隔离还促进了内核子系统热升级的实施



## 本课题创新之处

- 基于语言机制设计了一种通用、灵活、低开销的隔离内核架构
- 在隔离的基础上，我们演示了对内核子系统实施热升级的可能性
- 我们实现了一个原型操作系统并在商用操作系统中应用隔离内核架构，以证明其有效性
